1. Architecture, before and after

What was already right

Most of the metadata layer existed and was well built. Do not rebuild it: scripts/generate-route-heads.mjs already wrote a per-route title, description, canonical, robots directive, Open Graph set and JSON-LD graph into a separate build/<route>/index.html for all 39 routes, and scripts/generate-sitemap.mjs already emitted 34 canonical URLs.

The defect that made all of it inert

Every one of those 39 shells had a 108-byte body.

<noscript>You need to enable JavaScript to run this app.</noscript><div id="root"></div>

Perfect head, empty page. Each shell described, in structured data, a document that contained no text.

How the rendering was added

Build-time server rendering with react-dom/server, driven by the webpack and babel already in this project. No Next.js migration, no react-snap, no headless browser downloaded into a deploy pipeline. App.js now exports AppRoutes without a router; the browser wraps it in BrowserRouter and the prerender wraps the same component in StaticRouter. One route table, two entry points, so a route cannot exist for a visitor and be missing from the prerender.

Because every public page reads its copy from the CMS, the prerender fetches the three public endpoints once and writes that payload into each shell as window.__SCS_PRELOAD__. The client starts from the same data, so hydrateRoot adopts the server markup instead of discarding it. Measured in a browser: the post-hydration DOM is byte-identical to the prerendered markup on / and /about. No mismatch, no flash.

One devDependency was added: jsdom, already resolved in the lockfile. DOMPurify binds to a window at import and the article pages sanitize CMS HTML, so the prerender needs a DOM. The alternative was writing unsanitized CMS HTML into static files, which would hand every no-JavaScript reader an unsanitized document. yarn install --frozen-lockfile still passes.

2. Two production defects found during inspection

Blocker A. The host is serving index.html for every route, so all 39 shells are dead.

On the preview, /about, /join and /blog all return the homepage's title and <link rel="canonical" href="https://santacruzstrength.com/">. The correct file exists at build/about/index.html and is never served. A crawler sees one page pointing at itself from a dozen URLs.

The current live site has the same defect. santacruzstrength.com/blog serves the homepage title and a homepage canonical today. This is not introduced by the rebuild; it is fixed by serving static files before the SPA fallback, which is what deploy/ already specifies and the host is not doing.

Blocker B. The preview sends x-robots-tag: noindex, nofollow on every response.

Correct for a preview and fatal if it survives the cutover. It is a header, so nothing in this repository can remove it. Verify with curl -I against the production hostname before announcing launch.

5. What changed on the pages

Homepage

The hero H1, both CTAs and the whole visual system are untouched. Two sections were added, high enough on the page to be extracted and low enough not to interrupt the sell:

  • "What Santa Cruz Strength is", a factual definition block: name, category, address, what the floor supports, what is sold, and one standalone sentence on 24/7 member access. All four strings are CMS-editable and seeded, so the owner can correct them without a deploy.
  • "Built for strength training", the bridge between the category and the disciplines: powerlifting, Olympic weightlifting, strongman, general strength. Each claimed because the business already claims it in the About story, its hosted meet, or a member's own review. They are deliberately not links: four thin pages created to own four URLs is the mistake this section otherwise invites.

FAQ and disclosures, the crawlability fix

Three separate places were mounting content only on click, which means it did not exist in the document at all:

  • The homepage FAQ. Five answers were absent while the JSON-LD in the same file encoded all five. The schema described a page the page did not contain.
  • Six of the nine membership plans, including every couples and weekend tier, behind the "See more plans" toggle. An answer engine asked what a membership here costs could see three prices.
  • The membership FAQ answers.

All three now render into the document and hide with display:none when collapsed: present for anything reading the HTML, invisible and out of the accessibility tree for anyone who has not opened them, with aria-expanded and aria-controls added on the toggles. Verified in a browser: 12 plan cards in the DOM, 3 visible, page height unchanged.

Every "Save X%" now prints its baseline. All six percentages were checked against the published $120/mo month-to-month rate and all six are correct:

Personal training page

It had a hero, a four-item list and a form: enough to say the service exists, not enough to say what buying it involves. Added: How personal training works (inquiry → a coach makes contact → you meet at the gym), What happens during your first consultation, and Meet the coaches. Only steps the business actually performs. No rates, package sizes, session lengths or cancellation terms were written, because none is published anywhere and none has been confirmed.

Article dates, an accuracy fix

Every article displayed a publication date read from created_at, which is the moment the seeder inserted the row. All 27 articles reported the same date, and that date moved forward every time the backend restarted, so today the whole corpus claimed to be published today. The build-time JSON-LD already omitted datePublished for exactly this reason; the visible page now agrees with it. When a real per-article date exists, put it on the post record.

Payload

267.31 kB JS gzipped, 19.66 kB CSS, unchanged to within 78 bytes despite the added sections. A commented-out PostHog session-replay block and a commented-out Meta Pixel block were deleted from public/index.html: 2.3 kB of dead script text that was being copied into all 39 shells, about 90 kB of served bytes for code that could never run. 8. Evidence gaps — the owner has to answer these

Every one of these is a place the site declines to state something rather than estimating it. None was filled in.

  • Day pass hours. The live site publishes three different answers. This repo says 9:00 AM to 6:00 PM, the live site says 9am–9pm twice, and staffed hours end at 2pm on Sunday. Somebody buys a $20 pass and drives to a locked door until this is settled. This is the reason openingHoursSpecification is absent from the schema.
  • 24/7 access. Published on the homepage as a standalone sentence. It is the business's own claim, in the membership terms of every full plan, on the live site, and in a member's review. Confirm it is still true before launch; it is the sentence most likely to be quoted back at you.
  • Personal training rates and packages. Published nowhere. No offers node in the Service schema, no price on the page.
  • Equipment counts. Rack, platform and bench counts, specialty bars by name, and the chalk and dropping policies. 26 [FACT NEEDED] markers across the article corpus are waiting on exactly this.
  • Coach credentials. No bios were generated. Two trainers, Morghan King and Syon, have no photograph and render a placeholder. That needs a camera, not code.
  • Weekend Warrior access. Whether those tiers include 24/7 access within their three days.
  • Review provenance. The six testimonials are verbatim and unattributed, matching the live site. No dates or sources were invented. The data model can carry them when they exist.
  • Minimum age and whether a parent must attend.
  • Events. /events renders 662 characters because no events are published. Honest, and thin. Either publish one or accept the page is a stub.
  • The two canonical consolidations in the migration table: canonical or 301.

9. Not done, and why

  • No /gym or /equipment page. The brief asked for the hub to be possible, not invented. Every fact it would contain is an unanswered question above. Creating it now means creating a thin page, which the brief also forbids.
  • No new analytics property. GA4 stays behind its three gates. Two events that had nothing behind them were added, membership_view and get_directions; the other six the brief named already exist under names GA4 has been configured against, and the mapping is recorded in src/utils/analytics.js rather than the events renamed.
  • No Core Web Vitals numbers. Nothing was measured, so nothing is reported.

10. Remaining blockers before production

  1. Static-first serving. Until the host resolves /about to build/about/index.html, all 39 shells are unreachable and every page reports the homepage canonical. deploy/ has working configs for Netlify, Cloudflare Pages and Vercel. Prove it: curl -I <domain>/nothing-here must return 404 and curl -I <domain>/staff/dashboard must return 200.
  2. The x-robots-tag: noindex, nofollow header must be gone from the production hostname. Check it with curl -I, not by looking at the page.
  3. The build needs a reachable backend. PRERENDER_API_URL must point at a seeded API at build time. Without it the prerender skips loudly and the shells stay empty; with an unseeded database it refuses to run rather than publishing empty pages that look finished.
  4. The day pass window should be settled before the site goes live publishing an answer that contradicts the other two answers already published.

Accuracy over completeness. Where a fact was unavailable the page says less, and this document says which fact and who has it.

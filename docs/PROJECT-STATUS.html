4. The lead sequence, end to end

Visitor lands on a marketing route | v Quiz or form. Consent is three separate choices: service, email marketing, SMS marketing. Never bundled. | v POST to backend. Lead is persisted FIRST with attribution, request id and consent, BEFORE success returns and BEFORE any provider is contacted. | v Outbox creates inert delivery intents. Nothing sends from the request path. | v Dispatcher, fail closed. Allowlist, suppression, consent check, Pacific quiet hours, bounded retry, quarantine on ambiguous outcomes. | | | v v v Resend Twilio SMS GymMaster prospect ack mail (consent only) (dry run contract today) | v Staff work the lead in the CRM through twelve stages: new, acknowledged, contact_attempted, contacted, tour_booked, tour_confirmed, attended, no_show, trial, membership, lost, reactivation_eligible | v Visit. A coach completes signup in person. Memberships are not sold online.
Two rules the code enforces that most systems get wrong.
  1. An automated acknowledgement is not human contact. Recording contact requires an explicit staff event.
  2. A tour form records a request, not a booking. It becomes an appointment only when staff and visitor agree a time.

Emergent build model

The donor's .emergent/emergent.yml names the container image fastapi_react_mongo_shadcn_base_image_cloud_arm, so Emergent rebuilds inside a managed container rather than deploying a local artifact. Assume no Chrome in that image. Any prerender step must therefore either run locally with its output committed, or degrade to the current route-head shells without failing the build. Confirm the model before relying on it.
